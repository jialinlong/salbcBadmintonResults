# 页面跳转性能日志设计

## 目标

为“记录比赛”和“历史记录”页面补充可关联的分段耗时日志，以便用户启动小程序、复现 2–3 秒等待后，将客户端控制台与云函数日志提供回来，进而区分页面生命周期、网络/冷启动、数据库查询和客户端渲染各自耗时。

本次只增加诊断日志，不调整查询、缓存、加载状态或页面行为。

## 日志格式

所有日志使用固定前缀：

```text
[PERF][match][trace-id] client:cloud:getAllPlayers:start
[PERF][match][trace-id] cloud:players-query:end durationMs=123 count=42
```

字段包括：

- 页面：`match` 或 `history`
- `traceId`：由客户端为每次云函数请求生成，并随请求参数传入云函数
- 阶段名称：说明事件发生于客户端还是云端，以及具体操作
- `durationMs`：阶段耗时
- `count`：仅记录返回条数等非敏感规模信息
- `invocation`：云函数当前实例的调用序号；序号 1 表示该实例首次调用，可作为冷启动候选信号，但不直接宣称一定是冷启动

不记录球员姓名、密码、队伍、比分、完整请求或比赛详情。

## 记录比赛链路

客户端 `match.js` 记录：

1. `onShow`
2. 权限检查结束
3. `getAllPlayers` 调用开始/结束/失败
4. 球员整理和拼音转换耗时
5. `setData` 回调触发，表示数据已提交到视图层

云函数 `getAllPlayers` 记录：

1. 调用开始、实例调用序号
2. 球员查询耗时和数量
3. 当日比赛查询耗时和数量
4. 云函数总耗时或失败耗时

## 历史记录链路

客户端 `history.js` 为筛选项和首屏历史分别生成 `traceId`，记录：

1. `onLoad`、`onShow`
2. `getFilterOptions` 调用开始/结束/失败
3. `getHistoryDays` 调用开始/结束/失败
4. `processGroups` 耗时
5. 最终 `setData` 回调耗时

云函数 `getMatchStats` 根据请求类型记录：

- `getFilterOptions`：每一批数据库查询耗时、批次数量、累计数量、总耗时
- `getHistoryDays`：日期聚合耗时、日期范围查询的每批耗时、总数量、总耗时
- 公共信息：`traceId`、实例调用序号、请求类型、成功或失败总耗时

排行榜等其他请求继续正常执行；只输出必要的统一调用总耗时，不改变返回值。

## 错误处理

日志代码不得影响业务流程。失败日志只读取已有错误的 `message`，并继续沿用现有异常处理和用户提示。`traceId` 缺失时云函数生成本地后备 ID，保证日志格式完整。

## 验证

- 为纯日志辅助函数编写 Node 单元测试，先验证缺失实现时失败，再实现最小功能。
- 对修改后的五个 JavaScript 文件执行 `node --check`。
- 运行单元测试并确认全部通过。
- 检查 git diff，确认没有查询顺序、缓存或 UI 行为变化，且没有敏感字段输出。

## 交付与复现

用户部署两个云函数并启动小程序后，依次复现：

1. 冷启动后首次打开“记录比赛”
2. 返回首页后首次打开“历史记录”
3. 记录一场比赛后再次打开“历史记录”
4. 短时间内重复打开两个页面

随后提供包含 `[PERF]` 的客户端日志和云函数日志，即可按相同 `traceId` 还原完整耗时链路。
